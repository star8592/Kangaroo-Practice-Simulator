## 2. 灾备目标与威胁模型

必须同时覆盖：① 云服务器/系统盘永久损毁；② 主备链路失效或本地卷损坏；③ 本地主机 TPM/主板损毁；④ 文件损坏、重放旧回执、SSH 身份欺骗、数据过期；⑤ 密钥轮换后旧备份仍须可解密；⑥ 登录/考试/支付/微信关键业务依赖不能仅靠数据解包完成恢复。

**推荐双通道密钥保管**（两者独立，任何一种损坏不应导致无法恢复）：

A. 本地 TPM2 绑定的加密凭证，供本地主机灾备演练使用，保持已实现的 `systemd-creds --with-key=tpm2`、0600、0700 和无持久明文设计。此通道不是离开本地主机的灾难恢复密钥。

B. 离机的**独立离线加密密钥封存**，由授权人保管在独立的加密介质/合规密码管理器离线应急包内，最好双份异地保管、定期检测可读取。封存密钥不得通过 Chat、Git、Issue、PR、CI、工单附件或普通日志传递；不可仅保留在云端、本地主机或与其绑定的同一 TPM。恢复所需密码/解锁因子也要有经授权的离线可用方案，避免循环依赖。

**操作授权：**真实生产密钥的读取/转移/封存、提权、受限 SSH 身份更换、新云主机恢复，均按 `ENGINEERING_OPERATING_SYSTEM.md` 的 L3 执行显式批准与可撤销变更；不能自动从 CI 或聊天触发。密钥内容、敏感哈希指纹与明文恢复数据不得出现在验收材料中。

## 3. P0-1：TPM 许可阻塞的无密钥诊断

先**只检查元数据**，禁止为了验证 TPM 而读取生产口令。

1. 核对 `systemd-creds --version`、`systemd-analyze has-tpm2`、`systemd-creds encrypt --help`、`id`、`ls -l /dev/tpm* `、当前用户会话状态，以及有无容器/权限沙箱；保留输出时脱敏主机账号和路径。
2. 使用**纯合成密钥**测试当前用户执行 `systemd-creds encrypt --with-key=tpm2` 和解密是否稳定，至少连续成功三次，并记录退出码；此为独立显式硬件准入，不使用生产密钥。现有准入测试：`SOCTHINK_RUN_TPM_FIXTURE=1 python3 scripts/test_tpm_offsite_recovery.py`。
3. 若报 `org.varlink.service.PermissionDenied`，先核对系统 TPM 设备 ACL/用户组、udev、polkit/varlink 服务访问策略、系统日志和 systemd 版本，并在隔离合成样本上验证官方支持的用户作用域选项是否适用。**不要假定错误一定来自单一原因**。
4. 禁止改成 `--with-key=null`、关闭 TPM 验证、将生产口令复制为明文文件或用 CI/用户服务无授权提权；修复权限必须可审计、最小权限且不扩大日常拉取服务权限。
5. 未通过前 `TPM_NATIVE_ACCEPTANCE=BLOCKED`；不得执行生产封存脚本。

权威参考：[systemd-creds(1)](https://www.freedesktop.org/software/systemd/man/latest/systemd-creds.html) 与 [systemd CREDENTIALS.md](https://github.com/systemd/systemd/blob/main/docs/CREDENTIALS.md)。尤其注意 TPM-only 凭证只能在原 TPM 解密，不能用作主板损毁后的唯一恢复手段。

## 4. P0-2：封存与离线验证步骤

以下步骤需在受控机器、授权时段执行，**这里只描述操作与证据，不包含任何密钥内容**。

1. **快照基线**：确认最新成功云端备份和本地主机密文、`.sha256`、源恢复回执及本地回执全部存在，现有副本不得被新测试覆盖或删除。记录归档标识、文件数量、时间与 SHA-256 校验结果（不要公开完整可关联数据指纹）。
2. **TPM 方案**：合成硬件准入 PASS 后，由授权操作员执行已经审核的 `seal_offsite_recovery_tpm.sh`，验证不落盘明文、同一个来源密钥的封存/解封指纹一致、已有凭证不可被轮换覆盖；只报告 `TPM_ESCROW=PASS` 的非敏感元数据。
3. **离机方案**：另行制作与 TPM 完全独立的受控加密离线应急密钥包，填写保管人、位置类别（非精确机密地点）、介质清单编号、访问审批、保管交接与下一次验证日期。不得将设备与解锁因子放在同一个不受控位置。
4. **真实独立解密**：物理或网络隔离原生产云端；从本地主机实际密文副本出发，使用 TPM 凭证执行 `offsite_restore_drill_tpm.sh` 并保留合格的 PASS 回执。另在**与生产云端、本地主机 TPM 均独立**的隔离恢复环境中，使用离线应急密钥包解密至少一个真实归档；验证所需学生数据、考试记录、计算记录、题目资产及应用结构性一致性。
5. 恢复环境采用短生命周期受控目录/加密临时卷，清理后核查无明文残留；避免把真实学生信息上传 CI、GitHub 或共享测试环境。模拟数据运行可纳入自动 CI，真实数据只在受控环境演练。
6. 密钥轮换采用**先封存并验证新旧密钥、再切换生产加密、最后验证新备份**的双代策略；历史密文未过保留期不可丢弃对应解密密钥，严禁在旧密钥可用性未证实时删除旧备份。

## 5. P0-3：故障注入与权限收敛

| 试验 | 预期行为 | 证据要求 |
| --- | --- | --- |
| 原云端网络完全不可达 | 仅凭独立副本+离线密钥可恢复 | 断网证据、独立恢复 PASS |
| 最新密文损坏/截断 | hash fail，禁止误报成功；保留前代 | 错误码、未覆盖正常副本 |
| 错误密钥/密钥轮换 | 解密拒绝，历史旧归档可恢复 | 两代凭证与回执（无秘密） |
| 旧回执/重放/备份过期 | freshness 失败、产生告警 | 告警实际送达与时间戳 |
| 云端 SSH 身份变化/断连 | 拒绝连接，既有备份保留 | Host key 校验、非成功状态 |
| 本地卷不足/不可写、TPM 不可用 | 禁止删除可用备份或宣称恢复 | 故障日志、保留策略验证 |
| TPM/主板永久不可用 | 通过离机密钥独立恢复 | 新恢复主机完成解密验证 |
| 定时中断与重试 | 原子回执，幂等续传，不吞失败 | systemd 状态与健康回执 |

生产端当前备份拉取借用 root 管理身份。单列 L3 子任务，将其替换为**单用途、只读、只能访问必要加密制品**的身份与受限命令；先验证新身份工作并测试拒绝非备份路径访问，再回收旧链路，避免造成备份中断。

## 6. P0-4：新云服务器完整业务恢复

仅在隔离环境执行：基础系统与应用版本重建 → 非秘密配置恢复、机密由专门密钥管理重新注入 → 数据和资产恢复 → 权限/文件属主/配置校验 → Web 与微信相关 API、家长登录、计算首题、考试提交与持久化、PDF 报告、支付**沙箱/非真实扣款**及回调幂等验证 → DNS/入口切换演练 → 回退路径验证。

生产恢复期间应有写入冻结/回放策略，防止新旧环境同时写入或重复扣款；不得在演练中对真实用户执行真实支付/发信。现有在线 tar 不是跨文件事务一致性快照，需确认 JSON/JSONL 写入时的一致性，才能将该副本视作业务级可恢复点。

**RTO** = 从事故宣告/恢复启动到关键业务达到验收状态的实测用时；**RPO** = 从事故发生时间到最近一个已证实一致、可恢复的数据恢复点的时间间隔。数据延迟必须按实际备份结束时间与数据一致性测量，不能仅凭 24h timer 推算已经达标。未经测量均为 `UNKNOWN`。

## 7. 运行中的持续门禁与封板定义

- 备份任务实际成功（不是仅 timer enabled）、最近一次备份年龄、备份分代数量、原云与异机剩余容量、SHA 完整性、恢复演练是否过期均须定期采集。
- 告警须验证**确实送达**负责人的可行动渠道，模拟告警解除与恢复流程；监控盲点单独入 Issue。
- 不可更改/删除最后一份健康归档；清理保留策略必须先有足够历史恢复点、严格目录匹配与审计回执。月度做合成演练，定期做受控真实恢复演练，关键密钥/硬件变更后重新验证。
- 发布结论由非秘密的机读 JSON 回执与审查签字构成，建议字段：`backup_id`、`source_sha_verified`、`local_sha_verified`、`key_escrow_tpm`、`key_escrow_offline`、`cloud_disconnected`、`data_restore_verified`、`business_uat`、`rto_seconds`、`rpo_seconds`、`evidence_time`、`release_sha`。UNKNOWN 不能默认成 PASS 或 0。
- **Issue #82 可关闭条件**：TPM 准入/生产封存与离机密钥独立恢复、故障注入、只读备份身份、分代/空间/密钥轮换、告警实达、完整跨服务器业务恢复、实测 RTO/RPO 均有可复核证明且经 L3 审批；不满足任一项保持 OPEN。
