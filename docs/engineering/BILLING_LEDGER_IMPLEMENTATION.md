## 本阶段实际代码
1. ops/db/001_billing_entitlements.sql：单独、可重复运行的 schema（8 表，保留产品/订单/支付事件/权益/已验证家庭关系/配额/消费幂等/审计）。
2. src/lib/billing-ledger.ts：可信创建订单、按支付官方核验结果结算、同计划并行续费串行化、退款撤销、身份归属查询、原子扣额、幂等与重放检测。
3. src/lib/access-context-server.ts：仅信任服务端身份，并要求同时通过家庭原记录和账本双重关系后才可继承权益。
4. GET /api/access/me：只读展示；没配置正式账本时维持免费预览；数据库配置后读权益，访问失败 503 而不伪装为免费。
5. scripts/test_billing_ledger.ts：只在 localhost 且数据库名以 _ci 结尾的隔离数据库执行，自动重建/复验 schema；被 GitHub CI PostgreSQL 服务调用。

## 不可跨越的发布安全线
- 生产服务器现为 Node.js 20、现有用户信息存于私有 JSON。新账本 PostgreSQL **不是直接在生产旧数据库上建表**；需事先准备独立、安全、备份完成的数据库，并单独迁移和测试连接。
- 绝不提交数据库口令/微信密钥，SOCTHINK_BILLING_DATABASE_URL 仅以 root-only 的 systemd 环境文件/secret manager 注入。
- 密码和 URL 不写到日志。数据库 TLS 与可信 CA 必须在上线前落实。最小授权 DB 用户不可任意建表/删库，迁移使用独立角色。
- 不在用户回调/HTTP 请求参数里接收 paid=true、verified=true 来授予权限。微信签名及官方查单是未来付款适配器职责。结算内部接口无公开 HTTP route。
- 只有满足金额、币种、订单 ID、交易 ID、签名+官方状态核验后才允许调用 settleVerifiedOrder。
- 账本启用前后，现有免费样题、计算、基础报告、已提交成绩不受影响；所有进程/数据库出故障时用户看到明确重试信息，不能无限空白。
- PostgreSQL 备份需包含 schema+数据与已付费流水；需要异地备份、恢复演练、审计留存和限频。
- 当前 PaymentAdapter 尚未实现，对生产绝不生成会员权益，也绝不自动开启付款/收费。

## 回滚策略
代码采用 immutable runtime，由已通过 CI 的 commit 发布；如版本引发故障，原运行版本链接回滚。
账本迁移保持 additive，不因业务回滚删除数据库；禁用会员强制门/支付入口后免费内容仍可正常使用。
已支付订单不可简单在数据库中 DELETE；必须通过可追溯补偿记录处理。
