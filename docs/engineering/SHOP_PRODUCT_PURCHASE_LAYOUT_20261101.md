# SOCTHINK 原创资料商城：商品页面与支付交付流程（2026-11-01）

## 问题根因

用户 2026-11-01 的实机截图显示：原商品详情单独采用 740px 中央窄卡片，而站点统一内容宽度为 1440px。结果是站头、商品详情、页脚不在一个布局系统。页面显示 ¥1.99 却不能付款，是因为生产 Native 新收款开关尚未通过正式实付交付验收；不是一个按钮丢失的问题。

本次更改不用补丁式居中卡片，也不新建任何支付账本。

## 唯一设计规范

- 跟随全站 --layout-wide / --page-gutter / --portal-* 变量；商品列表和商品详情宽度统一。
- 桌面：左商品内容与文件证据，右 310—360px sticky 付款卡。窄屏：标题、购买区、详细说明按顺序单列。
- 优先内容：真实商品名称、商品价格、付款动作及状态、真实 PDF 文件名和大小、购买交付路径、完整售后条款。
- 目前没有已经授权的实际 PDF 内页预览，不用虚构样张图片。文件信息展示必须明确注明“非内页样张”。
- 一个微信账户完成登录、购买、订单查询、下载。不要创建新的家长/学生/PIN 模型。

## 支付状态定义

1. 新收款开关关闭：明确显示“微信支付尚未开放”的禁用状态，不暴露会创建订单的可点按钮，也不扣款。
2. 收款经真实支付验收开放但未登录：引导微信登录，返回当前商品详情。
3. 收款已开放且已登录：右侧直接复用 NativeCheckoutPanel 的 compact 模式。这只是 UI 展示，仍使用原有同源 Checkout POST、服务器价格、用户主动勾选售后条款、限时二维码、本人订单轮询。
4. 微信官方独立查单结算成 paid：转到 /account，已购商品有受保护的完整 PDF 下载接口。
5. 已拥有权益：优先显示下载按钮，不能重复创建同一商品的待支付订单。
6. 新收款紧急关闭时，历史已付商品仍应可以下载，不得因为收款开关关闭抹除权益。

## 产品导航

- /shop：13 个真实商品的列表与详情入口。
- /shop/{id}：完整商品展示与可用时的微信收银台，避免跳转另一个长套餐列表找入口。
- /resources：在线竞赛训练检索，直达原创 PDF 商品商城，不把练习题当可售资料。
- /account：唯一正式订单查询和下载位置。

## 真实验收与上线限制

2026-11-01 下午最新正式审计只有 NEW_CHARGES_DISABLED 阻断，13 个 SKU 与私有 PDF 资产经核验存在，微信官方只读签名查单真实通过，微信官方结算任务正常运行，但新站生产真实订单数为零。

本次布局代码不修改生产收款变量。须分别保留三类证据：商品页与手机布局上线通过；一笔合法真实微信付款的官方签名查单结算和订单 paid；同一买家账户实际 HTTP 200 PDF 下载并与入库 SHA-256 一致。三项不能互相替代。只读查询 ORDER_NOT_EXIST 不是下单或付款证据。

由于 Native 是 PC 微信扫码交易，手机浏览器 H5、微信内 JSAPI 和小程序支付需要各自获准后才能声明移动端收款可用。
