# 事故响应与生产恢复 Runbook

## 事故优先级

- P0：支付错误、跨用户数据泄露、学生无法正式交卷、服务全停。立即冻结发布，保护证据，执行回滚/隔离，核实用户与账本影响。
- P1：登录或主要训练路径不可用、部分正式考试受影响、订单无法履约、定时任务系统性停止。尽快恢复服务并升级负责方。
- P2：单页视觉缺陷、单一官网来源采集失败而其它来源正常。记录与批次修复，不当作全站故障。

## 发现 → 控制 → 恢复 → 验收 → 复盘

1. 保存原始事实：首次发现时间、用户影响、受影响 SHA、请求 ID、相关 systemd 与 API 状态。日志截取必须屏蔽 token/PIN/学生个人信息。
2. 明确事件负责人及故障域。L3 先避免不可逆的数据库/资金变更。通知责任人，记录处理动作和时间。
3. 只使用正式自动发布/不可变制品的 rollback，而不是混用旧部署工作流。对数据变更先恢复快照或执行经演练的逆向迁移。
4. 恢复后分别核验公网 SHA、首页、登录、考试权限、真实答题/交卷及订单链路；对于微信也必须独立验收客户端发布身份。
5. 异常来源页面可排队等待重试，但不能因单一来源失败抹去所有成功记录，也不能未审核即变更报名日期。
6. 事件结案必须有修复提交、故障发生到检测与恢复的时间、是否造成回滚或返工、影响数量、缺失测试、后续责任人与截止时间。

## 生产只读检查

以服务器当前正式 SHA 运行：

    cd /opt/socthink-math
    EXPECTED_SHA="$(cat .release/deployed_sha)" STRICT=1 bash ops/engineering/production_readiness.sh

脚本只读，诊断服务与公网上线状态，不触发重启/部署/写数据。输出 SOURCE_WATCH_* 是历史观测，不代表每条来源都成功。备份与异机恢复及微信平台正式发布没有独立证据时始终输出 UNKNOWN。

## 明确禁止

- 口头声称“已上线”却未核实公网发布回执。
- 用 Taro 构建通过代替微信真机与正式上线证据。
- 把监测任务的 timer active 误认为最近一次任务执行成功。
- 在恢复过程中清空私有用户目录、删除日志/证据或在未经备份下直接覆盖数据库。
- 通过改成 root 或移除敏感权限/证据门禁来使生产绿灯。
