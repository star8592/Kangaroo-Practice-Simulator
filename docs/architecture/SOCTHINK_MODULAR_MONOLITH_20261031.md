# ADR 2026-10-31：SOCTHINK 模块化单体与减法式工程治理

状态：采纳，逐步落实。范围：综合考试门户、微信小程序、考试训练、资料库、身份支付、Rust业务内核和生产发布。

## 1. 发现的问题

本轮代码检查确认，原公共质量脚本有64条显式step，其中大部分串行运行在普通发布路径。考试计算、竞赛来源监控、支付回调、远端备份、TPM离线恢复演练、品牌检查、构建和部署协议被人为绑定在一条同步链路。工程控制自检又强制规定备份及TPM检查必须出现在网页质量脚本中；package.json的prebuild还强制执行竞赛来源监控。因此即便只更改首页设计，某个无关系统的失败也可能阻止发布。

根因是边界不清和反向依赖，不是测试数量不够。解决方向是拆开责任和执行时机，而非叠加补丁、兼容代码、审批关卡、第二套发布器。

## 2. 技术选型：模块化单体优先

不按每个考试类别、资料来源或付款渠道拆微服务。保留一个现行前端与一套账户入口，逐步形成一个Rust业务核心，Rust内部按边界分模块。跨进程仅在实测有必要时使用明确、版本化的接口；不预先引入Kafka、事件总线、服务网格、工作流引擎或额外数据库。

现有Next.js/React已经承担SEO和网页渲染，因此本期不并列引入Vue；微信小程序继续共用既有后端业务合同。避免两套前端框架、两套权限、两套SKU和两套内容权威库并存。

架构方向：

  Web Next.js  ──┐
                 ├── 同一API/身份及权益接口 ── 业务核心
  微信小程序 ────┘                              │
                                    ┌──────────┼───────────┐
                                    考试执行   支付账本   资料检索
                                    一次评分   一次授予   只读索引
                                    └──────────┼───────────┘
                                          各自的权威数据
  内容审核与正式发布成功 → 原子目录快照 → 单次更新事件 → Rust只读索引
  监控、报告生成、来源研究、灾备演练 → 读结果、独立诊断，不反向阻塞作答与支付。

## 3. 模块所有权

| 模块 | 唯一权威/写入者 | 不允许的依赖 |
| --- | --- | --- |
| 身份/用户 | 现有账户和微信身份系统 | 不依赖赛事内容、报告渲染、支付页面是否打开 |
| 购买/权益 | 现有订单账本及幂等授权流程 | 不依赖资源搜索、来源采集、封面生成 |
| 试卷/题目 | 现有私有题库与训练就绪规则 | 不能把只读缓存当成审核/版权授权 |
| 作答/评分 | 唯一交卷、评分、结果持久化路径 | AI报告失败不能阻塞保存成绩 |
| 资源目录 | 训练就绪信息生成的可丢弃投影，逐步由同一Rust Core查询 | 不储存答案、用户、订单或第二份题库 |
| AI报告与诊断 | 读取已提交的考试结果，按需分析 | 不参与交卷、扣费或权益原子事务 |
| 来源研究与备份 | 独立读、独立检查、按其职责写证据 | 不能阻断普通网页设计改动 |

写入主链与分析读链分离：核心结果先可靠写入，外部模块只能消费已确认事实。没有消费者时也不应拖慢主事务。内容发布由现有唯一正式数据发布流程完成后发出一次更新事件，不建立循环轮询。

## 4. 发布只关注四个结果

发布流程仍沿用唯一的 GitHub main → CI → 不可变候选 → 原子切换/自动回退 → 公网精确SHA回执。

只检查四种能让客户受到直接损害的结果：
1. 固定代码能构建并启动；
2. 账户权益、付款状态、考试权限及评分不会错乱；
3. 真实试卷、题量及训练库存不倒退；
4. 失败自动恢复上一份可工作的完整版本。

不要每一模块都引入重复审批、等待锁或额外发布门禁。这里的安全合同是必要正确性，不是新的审批层。正式发布器的单实例互斥、候选验证、自动回退和SHA对账保留。

## 5. 互不阻塞的两条工程泳道

普通发布：npm run verify:public。只做考试数学与输入协议、考试目录、账号权益/授权、交卷幂等、微信支付基本合同、代码静态检查和可启动构建。已有隔离PostgreSQL账本、原生微信小程序和浏览器点击CI独立执行；不重复加入灾备演练与内容采集验证。

深度诊断：npm run verify:full。原来的全部专项测试仍保存在extended_diagnostics.sh，可以人工按需运行，也可以由各模块独立运维。灾备负测试、竞赛来源观察、竞赛情报、声音素材、运营对账、额外课程专项失败不应冻结无关的公共网页发布。

prebuild不再同步要求内容研究或赛事来源监测全部通过；这些测试保留在完整诊断。构建仍保留来源权利和基础品牌有效性检查。

这次移除的是交叉阻塞，不是删掉用户数据保护。财务改动要验收财务，身份改动要验收身份，目录变更要验收目录；第三方来源异常留在来源团队处理。异常必须报告而不能被静默忽略，但不自动升级成全站停工。

## 6. 专业的改造方法

任何架构变更先写：输入/输出、唯一数据所有者、允许的依赖方向、失败隔离范围、可逆的改造步骤。优先消除重复实现和循环调用；有必要时重构主链路而非添加补丁。真实证据先于性能与收益承诺。

每项改动单独隔离工作树 → 现有合同测试 → 真实部署候选 → 回滚能力 → 公网实测。没有证据不声称完成。

Rust R1/R2当前仅代码进入生产版本，线上资源检索仍由Next.js执行。R3若要正式接管，必须先解决glibc兼容（本机2.43，生产机2.39）、单服务打包和原数据发布事件，一次切换后移除旧查询主路径，不长期保留两套服务。严禁为了追求“全Rust”制造一堆相互依赖的微服务。

## 7. 本次落地范围和回退

本次更改：
- 质量脚本公共路径从原本约60项同步检查缩到核心领域合同、代码检查和构建；
- 完整旧诊断脚本迁移到extended_diagnostics.sh，功能保留；
- 工程控制检查不再强制要求备份与TPM演练出现在普通发布质量脚本；
- prebuild解除赛事来源研究对普通构建的同步依赖。

本次不改账户、付款、真实试卷、自动部署器、生产数据库和资源权限。若公共基础合同失败、CI失败或候选发布失败，仍必须阻止错误版本并自动回退，而不是强制上线。
